# ECU25KVA — Standard Operating Procedure

*17 November 2026. For anyone joining the work: basic electronics and basic MATLAB assumed.*

## 1. What this covers

Every change to the 25 kVA ECU follows one loop: **change the source, check
it, regenerate, run `./verify.sh`, then commit.** This SOP gives that loop
for the four parts of the project.

| Part | Folder | What it is | Tool |
| --- | --- | --- | --- |
| Circuit simulations | `sim/` | 28 SPICE circuits, each with checks that prove a claim about the design | ngspice, run from Python |
| Schematics and boards | `hw/` (production), `prototype/` (bench board) | KiCad schematics and PCBs, generated by Python scripts | KiCad 10 |
| Firmware | `firmware/core` (engine logic), `firmware/stm32` (chip drivers) | C code that runs on the ECU | zig C compiler (in `.venv`) |
| Simulink model | `model/` | 20 component models plus `ecu25kva.slx`, the whole ECU; it generates the C in `firmware/gen` | MATLAB R2026a with Simulink, Stateflow, Embedded Coder |

```
   HARDWARE                                  SOFTWARE
 +-------------------------------+         +-------------------------------+
 | Circuit blocks                |         | Simulink models               |
 | sim/ - 28 checked circuits    |         | model/ - 20 components        |
 | (SOP 1)                       |         | in ecu25kva (SOP 3)           |
 +---------------+---------------+         +---------------+---------------+
                 |                                         |
                 v                                         v
 +-------------------------------+         +-------------------------------+
 | Schematic generators          |         | Generated C + hand-written C  |
 | hw/, prototype/ - Python      |         | firmware/gen + firmware/core  |
 | writes KiCad (SOP 2)          |         |                               |
 +---------------+---------------+         +---------------+---------------+
                 |                                         |
                 v                                         v
 +-------------------------------+         +-------------------------------+
 | Boards and fab files          |         | Build firmware                |
 | 4 layers - prototype/fab      |         | firmware/stm32                |
 | (SOP 2)                       |         | -> app_model_signed.hex       |
 +---------------+---------------+         +---------------+---------------+
                 | assemble                                | flash
                 v                                         v
 +-----------------------------------------------------------------------+
 | PROTOTYPE BOARD (STM32G474)                                           |
 | flashed over ST-LINK, J-Link, USB or CAN - bring-up guide first       |
 +-----------------------------------------------------------------------+
     ./verify.sh checks every box above before each commit (SOP 4)
```

The reference ECU is the **Bosch MD1CS162**: its terminal diagram is the
master pinout. The engine is a Kirloskar **3GK550ETA 4SR1**, 12 V system,
controlled by a **DSE4522** panel.

Nothing here has run on a real board yet. Everything is proven on the PC:
circuit simulation, firmware tests against an engine model, and the
Simulink closed loop.

## 2. One-time setup (Windows)

Do this once per PC. After it, every command in this SOP runs from **Git
Bash** in the project folder.

1. Install **Git for Windows** (it brings Git Bash) and **KiCad 10**
   (default folder `C:\Users\<you>\AppData\Local\Programs\KiCad\10.0`). KiCad
   also supplies the circuit simulator (`ngspice.dll`) and the Python used
   for boards.
2. Get the project: `git clone https://github.com/mohan4220/ecu25kva.git`,
   then `cd ecu25kva`.
3. Make the Python environment with KiCad's Python:
    - `"/c/Users/<you>/AppData/Local/Programs/KiCad/10.0/bin/python.exe" -m venv .venv`
    - `.venv/Scripts/python.exe -m pip install ziglang PySpice numpy schemdraw markdown pypdf`
4. Put the **KiCad 7.0.11 symbol library** in
   `C:\Users\<you>\opt\kicad7-libs\kicad-symbols-7.0.11` (the schematics
   were drawn against it).
5. Install **MATLAB R2026a** with **Simulink, Stateflow and Embedded
   Coder** (and Fixed-Point Designer). Only needed for the model.
6. Install **Google Chrome** (it prints the PDFs).
7. For flashing: **STM32CubeProgrammer** (ST-LINK) or the **SEGGER
   J-Link** software, plus an ST-LINK V3 or J-Link probe.
8. Check the setup: `./verify.sh`. It must end with **ALL PASS**.

`verify.sh` sets the KiCad, ngspice and symbol paths itself on Windows.
Only if a tool lives somewhere else, set it before running, for example
`export NGSPICE_LIB="C:/…/ngspice.dll"` and
`export KICAD_SYMBOL_DIR="C:/…/kicad-symbols-7.0.11"`. On Windows the
project's Python is always `.venv/Scripts/python.exe`; the README's
`.venv/bin/python` is the Mac and Linux spelling.

## 3. SOP 1 — Circuit simulations

Each circuit block is a SPICE file in `sim/blocks/` plus a list of claims
in `sim/run_sim.py`. A red **FAIL** means the **design** is wrong, not the
simulator, provided the simulator is a known-good version.

**Run them**

1. All blocks: `.venv/Scripts/python.exe sim/run_sim.py`
2. Some blocks: add part of a name, e.g.
   `.venv/Scripts/python.exe sim/run_sim.py injector`
3. Read the **second line** first: `simulator: ngspice-46 (…ngspice.dll)`.
   The suite has passed on ngspice **42 and 46**. Any other version prints
   a WARNING: fix that before trusting a FAIL.
4. Each block prints its claims as PASS or FAIL, with the measured value
   and the target. The last line must read **28/28 blocks pass**.

**Change a circuit**

1. Edit the netlist, `sim/blocks/<name>.cir`. It also opens in KiCad's
   simulator (Tools → Simulator), LTspice or plain ngspice.
2. If what the circuit must do has changed, edit its check in
   `sim/run_sim.py` (the function `check_<name>`). Never loosen a check
   just to make it pass: write down why the new limit is right, beside it.
3. Run the block, then all blocks.
4. Carry the new part values into the schematic generator (SOP 2), and into
   the circuit page: `.venv/Scripts/python.exe sim/build_circuit_page.py`.
5. Write the reason in `docs/decisions-log.md`.

**The word FAIL inside a `.cir` file is not a failure.** The result notes
at the bottom of each file record "what if" runs: a part at its worst
tolerance or temperature, and what the design did about it. For example,
the load-dump TVS moved to a 43 V standoff, and the CAN terminators to
50 ppm/°C thin film. Only `run_sim.py`'s output says pass or fail.

## 4. SOP 2 — Schematics and boards

The schematics are **generated by Python scripts**: change the script,
never the `.kicad_sch` file, or the next run overwrites your edit. In the
commands below, `KP` is KiCad's own Python:
`KP="/c/Users/<you>/AppData/Local/Programs/KiCad/10.0/bin/python.exe"`.

**There are two boards**

| Board | Folder | MCU | State |
| --- | --- | --- | --- |
| Prototype (bench board, 300 × 200 mm, screw terminals) | `prototype/` | STM32G474 | Routed; manufacturing files ready |
| Production (fits the Bosch housing) | `hw/` | NXP S32K148 | Placed and checked; outline and connector wait for the old ECU to be measured |

Both are **4 layers, 1.6 mm FR-4, Tg ≥ 170 °C**: L1 and L4 2 oz (parts,
power), L2 1 oz solid ground, L3 1 oz power and slow signals.

**Change the production schematic**

1. Edit the sheet's generator, `hw/gen_sheet_<sheet>.py` (power_input,
   rails, injector, metering_egr, sensors_analog, speed_inputs,
   discrete_io, can, connector, mcu).
2. Regenerate and check: `.venv/Scripts/python.exe hw/check_netlist.py`
   must print **schematic connectivity OK**; `hw/test_schlib.py` and
   `hw/test_pcb_rules.py` must pass.
3. Board: `$KP hw/gen_pcb.py`, then `$KP hw/check_pcb.py` (footprints,
   nets, widths, DRC) must print **ALL PASS**.

**Change the prototype**

1. The prototype reuses the production sheets plus
   `prototype/gen_sheet_mcu_stm32.py` and `gen_sheet_lab_io.py`. MCU pins
   live in `prototype/stm32_pins.py`, checked against ST's own pin data.
2. `.venv/Scripts/python.exe prototype/gen_prototype.py`, then
   `prototype/check_prototype.py` (**schematic connectivity OK**) and
   `prototype/stm32_pins.py` (**pin map sound**).
3. Board, in order: `$KP prototype/gen_board.py sync` (rename, add new
   parts), then `finish` (route what is left), then `fab`. A full reroute
   (`route`) needs Java and Freerouting and takes about 2 hours.
4. `.venv/Scripts/python.exe prototype/test_prototype.py`: every prototype
   check.

**Explain the circuits:** `docs/pdf/ECU-Schematic-Guide.pdf` puts every
sheet after a page on what it does, why, the simulations that prove it and
the model it feeds. After a schematic change, rebuild it:
`CHROME="C:/Program Files/Google/Chrome/Application/chrome.exe" .venv/Scripts/python.exe docs/build_schematic_guide.py`
(it plots the sheets fresh with kicad-cli).

**Draw it by hand:** `docs/pdf/ECU-System-Circuit.pdf` is the whole ECU on
one A0 portrait page: each block's circuit with its real parts and values,
joined by named wires (same name = same wire), plus the connector table.
Rebuild it the same way with `docs/draw_system.py`.

**See the board:** `docs/pdf/ECU-PCB-Prototype.pdf` is the routed prototype
PCB as 11 A3 sheets at 1:1 (blocks, connections, terminals, assembly, copper
layers, 3D). After a board change rebuild it with
`CHROME=... .venv/Scripts/python.exe docs/draw_pcb.py` (about 4 minutes; it
uses KiCad 10's kicad-cli and Python).

**Order the prototype:** upload everything in `prototype/fab/` (Gerbers,
`prototype.drl`, `bom.csv`, `positions.csv`). Select 4 layers, 1.6 mm,
outer 2 oz / inner 1 oz, Tg 170. Then follow `prototype/docs/bring-up.md`
step by step.

## 5. SOP 3 — The MATLAB Simulink model

`model/ecu25kva.slx` is the whole ECU in one model, and its buttons do the
rest: generate the C, build the firmware, flash the board. You edit the
component models; the buttons turn your edit into a board you can flash.

**Open it**

1. In MATLAB: `cd C:\Users\<you>\ecu25kva\model`
2. `addpath(pwd, fullfile(pwd,'lib'), fullfile(pwd,'test'))`
3. `open_system ecu25kva`

**What you see**

- **Buttons** across the top: Generate code, Build firmware, Bootloader,
  Flash (ST-LINK), Flash (J-Link), Clean project, Run all checks, Simulate.
  Select_PCB picks the board; only the prototype can be built today.
- **TRIGGERS**: a Stateflow scheduler firing initialisation, a
  per-cylinder event, and the 1 ms, 20 ms, 500 ms, 1 s and 10 s tasks.
- **MODEL**: the tasks, each holding the real component models.
  Double-click a grey **Model block** to open that component.
- **PLANT**: the engine, generator, fuel rail, valve coil and sensors.
  Simulation only; it is never flashed.

**The component models**

| Model | Kind | Does |
| --- | --- | --- |
| `ecu_sensors` | Simulink | volts to °C, kPa, bar; range faults |
| `ecu_safety` | Simulink | the trip decision: overspeed, lost crank, ignition off |
| `ecu_mode` | Stateflow | engine states OFF, WAIT, CRANK, RUN, SHUTDOWN |
| `ecu_spdst` | Stateflow | speed states OFF, IDLE, OPERATING, STEADY |
| `ecu_gov` | Simulink | speed governor (PI, droop, start ramp, idle) |
| `ecu_railset`, `ecu_rail` | Simulink | rail pressure setpoint and PI |
| `ecu_mucur` | Simulink | metering valve current loop (rail → current → PWM) |
| `ecu_egrpos` | Simulink | EGR valve position PID |
| `ecu_soi`, `ecu_injdur` | Simulink | injection timing and duration |
| `ecu_boostg`, `ecu_boostm` | Stateflow | 100 V boost rail: trip and warnings |
| `ecu_egrg`, `ecu_wifg`, `ecu_underg`, `ecu_relay` | Stateflow | EGR stall, water in fuel, underspeed, main relay |
| `ecu_j1939` | Simulink | J1939 message data to the DSE4522 |

**Change something**

1. Double-click the Model block, edit the component, **save it**.
2. **Simulate**: 20 checks run (start, 20 kW step, stop switch, sensors,
   injection, J1939, cascades); the plot is saved as
   `model/test/ecu25kva_sim.png`.
3. **Generate code**: C for every component goes to `firmware/gen/`.
4. **Build firmware**: compiles and checks the images
   (`firmware/stm32/build/`).
5. **Run all checks**: `verify.sh`. If the back-to-back test reports a
   difference, your model now behaves differently from the hand-written C
   in `firmware/core`. If you meant it, change that C to match; if not,
   undo the model edit.

Numbers such as gains and limits come from the C headers in
`firmware/core` (`ecu_params.m` reads them). Change a calibration there,
then rebuild only that model from its script: `build_all({'ecu_gov'})`.
**Never run `build_all()` with no argument** unless you mean to start
every model over: it rebuilds them from scripts and erases your Simulink
edits.

**Flash the board**

| Situation | Button or command | What goes on the chip |
| --- | --- | --- |
| New board, first test | `firmware/stm32/build/app_standalone.hex` over SWD | the application alone |
| Normal first flash | **Bootloader** | bootloader + application |
| Update after a change | **Flash (ST-LINK)** or **Flash (J-Link)** | `app_model_signed.hex`, the code from these models |
| Update without a probe | `.venv/Scripts/python.exe firmware/tools/ecu_service.py --link usb:COM5 --secret key.bin flash firmware/stm32/build/app_model.bin --sw-ver 0x00010000 --hw-min 0x0000 --hw-max 0xFFFF` | over USB or CAN, through the bootloader |

Before the first power-up, follow `prototype/docs/bring-up.md`: the LED
must blink at 1 Hz and the watchdog pin must show a falling edge every
10 ms.

## 6. SOP 4 — Check everything, then release

One command checks the whole project and names whatever failed. Nothing is
committed unless it ends with **ALL PASS**.

| Command (Git Bash, project folder) | Checks | Time |
| --- | --- | --- |
| `./verify.sh` | circuits, schematics, MCU pins, both firmware builds, the models against the C, 17 engine scenarios on both builds, service tool, STM32 build | about 10 min |
| `./verify.sh --boards` | the above + production and prototype board checks | + about 10 min |
| `./verify.sh --matlab` | the above + the Simulink closed loop (20 checks) | + about 5 min |

Use `--boards` after any schematic or board change, `--matlab` after any
model change.

**Release checklist**

- [ ] `./verify.sh` (with `--boards` / `--matlab` as above) ends with **ALL PASS**
- [ ] The reason for the change is written in `docs/decisions-log.md`;
      `docs/status.md` updated if the state changed
- [ ] PDFs rebuilt:
      `CHROME="C:/Program Files/Google/Chrome/Application/chrome.exe" .venv/Scripts/python.exe docs/build_pdf.py`
      (the combined book is `docs/pdf/ECU-Bible.pdf`)
- [ ] Commit: `git add -A` then `git commit -m "<what changed and why>"`,
      no AI credit lines (project rule)
- [ ] Push (`git push`) only after someone has reviewed it

## 7. Troubleshooting

Every row below has happened on this project. Read the first error line,
find it here, then rerun the same step.

| What you see | Why | Fix |
| --- | --- | --- |
| `run_sim.py`: "no ngspice", or all 28 blocks FAIL | the simulator was not found | install KiCad 10, or `export NGSPICE_LIB="<path to ngspice.dll>"` |
| a few blocks FAIL by small margins | a different ngspice version (line 2 shows it) | use ngspice 42 or 46 (KiCad 10.0.6 ships 46) |
| `verify.sh`: "symbol library" FAIL | KiCad 7.0.11 symbols missing | install them (setup step 4) or set `KICAD_SYMBOL_DIR` |
| `make: not found`, `.venv/bin/python: not found`, `cc: not found` | Mac/Linux commands on Windows | use `./verify.sh` and `.venv/Scripts/python.exe`; the scripts fall back to zig for C |
| Back-to-back test: "largest difference … FAIL" | a model and its hand-written C now behave differently | intended: update the C in `firmware/core`; not intended: undo the model edit |
| Hand-written build passes, model build fails | the glue between generated code and firmware (`firmware/core/model_glue.c`) | a Stateflow chart's outputs must be kept in static storage, never fresh local variables |
| Simulink: "model being referenced must inherit a sample time" | a block in a component has its own sample time | set it to -1 (inherited); component models are "sample-time independent" |
| Simulink: "Input data dependency violation" / algebraic loop | an output feeds back to an input in the same step | put a Unit Delay in the loop (the measurement reads the previous step) |
| MATLAB exits with only "MATLAB error" | another MATLAB session was still closing | wait a minute and run again |
| Flash: "no ST-LINK tool found" | programmer software not installed | install STM32CubeProgrammer (or OpenOCD), or the J-Link software |
| Rust simulator refuses the firmware: "ABI 4" | its binding is older than the firmware | known and left for now (decisions log §23) |
| Board blinks the LED at 2 Hz | the 8 MHz crystal did not start; running on the internal clock | check Y301 and its capacitors |

## 8. Rules that must not be broken

1. **100 V on the bench.** The injector boost rail (TP12) reaches about
   100 V, up to 119 V in a fault, and stays charged after power-off.
   Measure TP12 to GND and wait until it reads under 5 V before touching
   the board. Use a probe rated 300 V CAT II or better.
2. **An independent stop before any engine run.** The DSE4522 takes its
   speed from this ECU, so its overspeed trip is not independent. Have the
   standalone overspeed trip, or a fuel or air cut-off, within reach.
3. **Never hand-edit generated files:** `hw/*.kicad_sch`, `firmware/gen/`,
   `docs/pdf/`, `firmware/stm32/build/`. Change the generator, the model or
   the document they come from.
4. **One home for every number.** Calibrations and limits live in the C
   headers in `firmware/core`; the models read them from there.
5. **The Bosch MD1CS162 terminal diagram is the master pinout.** Where the
   KOEL harness drawing disagrees, Bosch wins.
6. **`./verify.sh` ends with ALL PASS before every commit.**
7. **Academic licence.** The MATLAB here is an academic licence, and every
   generated C file says so. Use it for learning and bench testing only.
   Before commercial use, regenerate all code under a commercial MATLAB,
   Simulink and Embedded Coder licence, then run `./verify.sh --matlab`.
8. **Leave the Rust simulator (`simulator/`) alone for now.**
