# Simulink / Stateflow model of the ECU application, with generated code

**Date:** 13 November 2026. **Asked for (owner):** "a complete state flow
model in MATLAB Simulink that is able to generate code, and the new
generated code we should be able to flash in our ECU". The owner left
the how to us ("do the best you can").

## Intent

The control and state logic is held in models that engineers can read,
simulate and change in Simulink and Stateflow, and the code that runs on
the ECU is generated from them. It must stay as trustworthy as the
hand-written core it replaces: the existing tests decide.

## Goals

- A Simulink/Stateflow model for every piece of application logic:
  the engine state machine, governor, rail-pressure control, injection
  maths, the trip decision, the protections (boost overvoltage, EGR
  stall, water in fuel, underspeed) and the main-relay after-run.
- Embedded Coder generates portable C99 from each, single-precision
  float, for an ARM Cortex-M4F: the STM32G474 (prototype) and the S32K148
  (production) alike.
- The generated code drops into the existing firmware at the module
  boundaries, behind a build switch, `ECU_MODEL`. With it on, the
  existing unit tests and SIL scenarios pass unchanged.
- A top-level model composes the pieces with a simple engine, so a
  start, a load step and a trip can be simulated in Simulink.

## Non-goals

- The platform layer stays hand-written C: crank-tooth decoding, the
  per-tooth injection scheduling, J1939, UDS, flash storage, the logs
  and the bootloader. They are event- and byte-driven, and already
  tested.
- The chip drivers (ADC, timers, CAN, USB, flash) are not modelled here.
  They are the separate "chip layer" still to write. Until it exists,
  nothing (model-generated or not) can be flashed and run on the board.
- No calibration changes: every constant is today's.

## Anti-goals

- A model that drifts from the C. So the constants are not typed twice:
  the build script reads them from the C headers and tables.
- A model that can't be rebuilt. The `.slx` files are generated by
  MATLAB scripts in `model/`, like the schematics are by Python.

## Approaches considered

1. **One model for the whole 1 ms step** (state machine, control,
   protections in one generated `ecu_app_step`). Clean on paper, but the
   state machine is driven from the crank-tooth interrupt as well as
   the tick (overspeed and sync trips act on the tooth), so it would
   either move per-tooth decisions to the tick (slower trips, the tests
   fail) or split one state machine across C and model.
2. **Drop-in components** (chosen). One model per module, each generated
   as a reusable function with its own state, wrapped by a thin C glue
   that keeps today's API (`gov_step`, `rail_step`, `safety_check`,
   `inject_dur_us` ...). The state machine is a Stateflow chart driven
   by commands (ignition on, tooth, run, trip, reset), so the tooth
   interrupt and the tick both reach it. The existing tests then check
   the generated code directly.
3. **Model the whole firmware including drivers** with the STM32
   Microcontroller Blockset. Ties the design to the STM32 only (the
   S32K148 needs NXP's toolbox, not installed) and throws away the
   tested platform code.

## Decided

- Models are built by `model/build_all.m`; code by `model/gen_code.m`
  into `firmware/gen/`, committed so the firmware builds without MATLAB.
- `ECU_MODEL=1` swaps the hand modules for `firmware/core/model_glue.c`
  plus the generated code. The hand modules stay as the reference until
  the generated code has run on the engine.
- Embedded Coder settings: ERT, reusable function with root I/O as
  individual arguments, inlined parameters, single precision, ARM
  Cortex-M.

## Left to the builder

Block layout, chart layout and naming inside each model; the engine
plant's detail in the top-level model.
